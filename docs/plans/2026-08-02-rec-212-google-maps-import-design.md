## Problem Statement

People already have valuable place collections in Google Maps and regularly share place content from Instagram and TikTok. rec.me currently exposes too much import machinery and asks people to rebuild personal metadata one place at a time. The existing review screen presents a bulk action, then opens the regular save sheet once per item. Importing a 37-place list can therefore require 37 save flows, while sharing one Instagram or TikTok post can still dump the user into a disproportionately heavy inbox/review experience.

That makes the migration path contradict the reason someone imported a list: they want their places accessible in rec.me now, while rating, notes, visit history, and sharing can happen later.

REC-212 replaces the prior REC-97 product assumption that every imported item must pass through the full regular save flow. It does not discard REC-97's useful source parsing, provenance, duplicate safety, or exception-review work.

## Demand Evidence

The triggering behavior is concrete rather than hypothetical:

- Joe reported that “a bunch of my friends already have Google Maps lists.”
- The desired job is migration at list scale, not individual capture: “I'm not realistically gonna go through and add notes for 37 places in LA.”
- The value threshold is immediate access: “But I want them accessible from the app.”
- The requested default is explicit: ratings should be optional and imports should “just auto save” the places.

This is directional evidence from a founder and nearby users, not yet a quantified acquisition study. The first release should therefore validate import completion and downstream use before expanding into provider account sync.

## Status Quo

### In-app import

1. Add shows one generic Import row for Instagram, Google Maps, TikTok, Notes, and other sources.
2. The import hub asks the user to paste links or place text into a large editor.
3. A public Google Maps list URL is expanded into individual candidates.
4. Import Review shows an unlabeled bookmark and checkmark on each ready row. Neither status is staged by default, so the interface does not clearly communicate Wanna versus Check-in or what will happen next.
5. `Save N` queues the items but opens the normal place-save sheet once per item.
6. Dismissing one save sheet cancels the remaining queue.

### Share extension

Google Maps can share a URL into `Save to rec.me`. The extension writes the share to an App Group inbox, confirms capture, and closes. The user must reopen rec.me, accept a Review prompt, and then encounters the same per-item save loop.

### Onboarding and ad entry

- Onboarding currently covers identity, location, contacts, friends, and notifications. It has no import step.
- rec.me deep links do not include an import route or campaign context.
- A link received while signed out can be retained in memory, but there is no dedicated import intent to resume after identity/onboarding.
- Pre-install ad intent is not preserved through the App Store today.

### Data and provider constraints

- The current importer accepts public Google Maps list links only.
- It uses an unofficial Google Maps internal list endpoint, so provider changes are an ongoing reliability risk.
- Import batches are staged locally until places are saved.
- The backend permits a null rating, but the iOS client currently supplies a synthetic 3/5 for an unrated Been save.

## Target User & Narrowest Wedge

### Target user

An iPhone user who already maintains at least one Google Maps list, is trying rec.me for the first time or responding to an import-focused ad, and wants the collection available without reconstructing it place by place.

### Narrowest worthwhile release

- One public Google Maps shared-list link at a time.
- A hard beta limit of 100 source items. The importer never silently truncates. Lists over the limit stop before resolution with: `This beta supports lists with up to 100 places. Choose a smaller list and try again.`
- Resolved places default to Wanna.
- New imported saves use place visibility `self`; the destination list uses list visibility `stealth`.
- No imported rating, note, visit date, tags, or user-selectable defaults.
- One confirmation commits all ready places.
- A private rec.me list preserves the Google list name and membership.
- Exact duplicates attach to the imported rec.me list without overwriting existing personal data.
- Ambiguous matches and failures move to a separate exception queue.
- The flow is available from an import ad route, onboarding, Add, and the share-extension inbox.

This release does not require Google account authentication, private-library access, background sync, or continuous mirroring.

## Constraints

- Preserve rec.me's four-tab navigation and existing Add entry.
- Do not require location, contacts, or notification permission before importing.
- Never infer Been, a rating, or a visit date from Google list membership.
- Never overwrite an existing status, rating, note, date, visibility, or other personal field during duplicate reconciliation.
- Use source/place fingerprints and stable operation IDs so retrying a batch cannot create duplicate saves or duplicate list membership.
- Treat the import as one user action with resilient per-item commits. One bad item must not roll back 36 successful items.
- Keep source provenance available for debugging without placing raw list contents or private place data in analytics.
- Persist authenticated batches and item outcomes in the server-backed REC-97 import repository. The App Group inbox may temporarily hold an unbound share envelope, but it is not the durable batch source of truth.
- Bind an unbound share envelope to an account only after the main app shows the active account and the user confirms the import. Once bound, it cannot move to another account.
- Provide an honest failure path for private, inaccessible, malformed, or provider-broken links.
- Gate public-list acquisition behind a server-controlled capability flag and remote copy. Paid acquisition cannot launch until provider/legal review and reliability monitoring are complete.
- The design does not authorize a TestFlight release, backend migration, or public campaign launch.

## Premises

1. A Google Maps list proves “keep this accessible,” not “I have been here.” The safest default is Wanna.
2. Migration is successful when the useful places become available, not when every candidate has been enriched.
3. Human attention belongs on exceptions. Ready items should not require item-by-item confirmation.
4. A single visible confirmation is enough because the user deliberately supplied the list and sees the count and fixed defaults before committing.
5. New imported saves use place visibility `self`; the destination collection uses list visibility `stealth`. Sharing can be intentional and reversible later.
6. The source list's organization is valuable. Flattening all places into a generic Wanna collection throws away context.
7. “Bulk save” is a UX promise, not necessarily one database transaction. The system should process each item idempotently and report partial success.
8. Ad intent must survive identity setup for an installed app. Exact first-install deferred-link behavior is a later distribution decision and should not block a useful onboarding import entry.

## Approaches Considered

### Approach A: Repair the current Import Review flow

Keep the generic hub and review screen. Default all ready Google items to Wanna and replace the per-item sheet loop with a true batch commit.

**Advantages**

- Smallest product and routing change.
- Improves Add and share-extension imports immediately.
- Reuses the existing review model.

**Disadvantages**

- Still feels like an administrative inbox rather than migration.
- Does not create a compelling ad landing or onboarding activation moment.
- Keeps users focused on reviewing rows before they have received value.

### Approach B: Dedicated “Bring your Google Maps list” migration flow

Create a Google-specific acquisition, confirmation, commit, and success flow that can be entered from ads, onboarding, Add, or a pending share-extension capture. Generic import review remains available for other sources and Google exceptions.

**Advantages**

- Matches the high-intent migration job directly.
- Can deliver value before permission prompts.
- Makes a 37-place list feel like one action.
- Produces a visible map/list payoff instead of ending in an inbox.
- Gives ad creative and onboarding one clear promise.

**Disadvantages**

- Requires new deep-link, onboarding-resume, batch-commit, and success-state work.
- Needs careful retry, duplicate, partial-failure, and optional-rating contracts.
- Must degrade gracefully when Google's unofficial list endpoint changes.

### Approach C: Mirror and continuously sync Google lists

Connect or scrape a Google source as a linked collection, periodically diff changes, and keep rec.me membership synchronized.

**Advantages**

- Eliminates repeated manual imports.
- Creates a strong long-term switching bridge.

**Disadvantages**

- Google account/API availability, unofficial scraping, deletions, rename conflicts, and status ownership make the contract much larger.
- Continuous sync can overwrite or confuse intentional rec.me curation.
- It is not required to validate the migration wedge.

## Concrete Flow Variants to Prototype

These are three interaction flows within the dedicated-import direction. None is selected yet.

### Flow 1: Instant import

```text
Ad / onboarding / Add
  -> Paste or share Google list
  -> Resolving progress
  -> Automatically save resolved places as private Wanna
  -> “37 places added”
  -> Map or source-named list
```

**Why explore it:** This is the strongest expression of “just auto save it.” The submitted list is the user's confirmation.

**Risk:** Users may want to verify the list, destination, or privacy behavior before rec.me writes dozens of places. A wrong/private/unexpected list creates a trust problem.

### Flow 2: Batch-first with optional row enrichment

```text
Ad / onboarding / Add
  -> Paste or share Google list
  -> Resolving progress
  -> All ready places visibly default to Wanna
  -> Compact rows with explicit Wanna / Check-in state
  -> Optional caret opens rating, note, date, and status details
  -> [Add 37 places] without opening any row
  -> Map or source-named list
```

**Why explore it:** This keeps the recognizable review list but reverses its hierarchy. Batch add is the primary path; row-level enrichment is optional. One action can add the entire list, while people who care about a specific place can still go deep before committing.

**Risk:** Too many expanded controls could still make the screen feel like homework. The collapsed state must stay compact, and edits must stage without requiring a per-row save.

#### Candidate review screen


Interaction hypotheses:

- Every ready row starts as Wanna; the default is visible in words, not inferred from iconography.
- The batch default control explains both concepts: `Wanna — Save it for later` and `Check-in — I've been here`.
- Selecting a different batch default updates every untouched row. Rows the user manually edited remain unchanged unless they explicitly choose `Apply to all`.
- Each collapsed row shows its current status pill and a disclosure caret.
- The caret expands inline optional fields. It never launches the normal save sheet.
- Check-in expansion offers rating, visit date, and note as optional fields; no synthetic rating is created.
- Wanna expansion may offer note and list choice, but should not display irrelevant rating/date controls.
- The bottom action is always visible when ready items exist. Its label is `Add N places`; the line above reports the Wanna/Check-in breakdown.
- Needs Help items are excluded from `N`, remain available after the batch add, and never block ready places.
- A user can add all ready places without expanding a single row.

### Flow 3: Map-first preview

```text
Ad / onboarding / Add
  -> Paste or share Google list
  -> Imported candidates appear on a temporary Map layer
  -> Bottom sheet: “37 found · 3 need help”
  -> [Keep all 34 ready places]
  -> Preview becomes the saved private list
```

**Why explore it:** The user sees the value before confirming. It makes the import tangible and may help catch a completely wrong list or region quickly.

**Risk:** Temporary pins can be confused with saved places, map fitting may be poor for geographically broad lists, and this has the highest UI/state complexity.

### Single/few versus many: one system, adaptive surfaces

The exploration now includes Instagram and TikTok share-extension imports, not only Google Maps. The leading systems hypothesis is **shared semantics and infrastructure with a presentation that adapts to item count**.

Source-specific acquisition remains different because extracting an Instagram post, TikTok, Google Maps place, Google list, or pasted text requires different parsing and recovery copy. After places are normalized, status, optional enrichment, duplicate handling, and saving should behave consistently.

Candidate presentation thresholds to prototype:

| Ready items | Surface | Primary action | Optional depth |
|---|---|---|---|
| 1 | Quick Add card/sheet | `Add as Wanna` | Change to Check-in; caret for rating, date, note |
| 2–5 | Compact review list | `Add all` | Explicit status per row; expand any row |
| 6+ | Batch review | `Add N places` | Wanna batch default; apply to all; expand exceptions or chosen rows |

These thresholds are test inputs, not decisions. The key behavior to validate is whether one adaptive component family feels coherent without forcing a one-item Instagram share through a large import inbox or giving a 37-place list a one-item save flow 37 times.

Working rules:

- A source never determines Wanna versus Check-in. New resolved places visibly default to Wanna.
- A one-item flow still explains `Wanna — save for later` versus `Check-in — I've been here`.
- Optional enrichment stays behind the same caret/disclosure pattern at every size.
- When a share unexpectedly resolves multiple places, the UI promotes itself to compact or batch review without changing semantics.
- Needs Help items remain recoverable but never block ready items.
- Share-extension capture should confirm what was captured and hand off cleanly; it should not expose parsing, inbox, and save-system complexity at once.

### Prototype questions

1. Does sharing/pasting the list already feel like sufficient consent, or do people want one confirmation?
2. Do people understand that new places default to private Wanna without editing every row?
3. Is the stronger payoff a populated Map or the preserved source-named list?
4. Does Map-first preview create delight or confusion about what is already saved?
5. After an ad or onboarding entry, where does a user expect to land when import finishes?
6. Does an adaptive 1 / 2–5 / 6+ presentation feel like one understandable system, or do extension imports need a distinct mental model?

### Entry behavior

#### Import-focused ad, app already installed — Gate 3

1. The ad opens a universal link such as `https://getrec.me/import/google?campaign=<id>`.
2. If signed in and onboarded, rec.me opens the dedicated Google import flow.
3. If identity is required, the app retains an import intent and resumes it immediately after identity.
4. Location, contacts, friends, and notifications do not run before the import.

Campaign identifiers must be allowlisted/coarsened for analytics. They must never contain a Google list URL or user place data.

#### Import-focused ad, app not installed — Gate 4

The MVP landing page carries the import promise and sends the user to the App Store. First launch prominently offers Google Maps import during onboarding, so the job can continue even without exact deferred routing.

Engineering should separately evaluate a first-party or approved deferred-intent mechanism. Gate 4 should not claim exact continuation until it is verified on a physical device across install, auth, termination, and retry. A deferred-intent vendor is not a dependency for Gates 1–3.

#### Organic onboarding — Gate 2

After required identity, show a skippable activation card before permission prompts:

> **Bring the places you already saved**
> Import a Google Maps list in about a minute. Ratings and notes are optional.

Primary action: `Import from Google Maps`
Secondary action: `Not now`

If the user skips, onboarding continues normally and the same entry remains under Add.

If the import succeeds, that success counts as onboarding activation: mark onboarding complete and open Map with the imported list filter active. Location, contacts, and notifications remain unset and may be requested later from contextual product surfaces. If the user cancels or exits before a successful commit, return to the next normal onboarding step. A source error always offers `Continue setup without importing`, so the user cannot become stranded.

#### Add — Gate 1

The existing Import row remains. Choosing Google Maps routes into the dedicated migration flow; other source types continue into the generic hub.

#### Share extension — Gate 1

A captured Google Maps list remains safe and unbound in the App Group inbox. On the next app activation, rec.me first shows an account-binding interstitial:

> **Import this list to @handle?**
> It will become part of this rec.me account.

Actions are `Continue`, `Not now`, and `Delete capture`. `Continue` binds the envelope once and opens resolving. `Not now` leaves it unbound in the seven-day FIFO queue. `Delete capture` removes it locally and cannot be undone. If the active account changes before binding, the interstitial updates to the new handle and requires a fresh confirmation; after binding, another account can neither see nor claim the batch.

If iOS does not permit reliably opening the containing app from the share extension, the extension must say exactly what happened: `List captured. Open rec.me to finish importing.`

### Screen and state design

#### 1. Acquire

Title: `Bring your Google Maps list`
Body: `Save the whole list to rec.me. You can add ratings and notes later.`

Primary paths:

- `Share from Google Maps` opens concise, illustrated instructions.
- `Paste a public list link` reveals the URL field and paste action.

Trust copy:

- `Your imported places start private.`
- `Only public shared-list links work right now.`

#### 2. Resolving

Show the source name when known and determinate progress when item count is available. Every state transition is persisted before new network work begins. The user can leave; the batch resumes from its last durable state when rec.me reopens. The UI does not promise uninterrupted iOS background execution.

Copy examples:

- `Opening LA Spots…`
- `Finding 18 of 37 places…`
- `You can leave this screen. We'll resume when you reopen rec.me.`

#### 3. Batch confirmation

The confirmation summarizes rather than demanding row review:

> **37 places ready**
> 32 new places will be saved as Wanna. 5 places you already saved will keep their details. All 37 will be added to a private list called LA Spots.

Primary action: `Add 37 places`
Secondary disclosure: `View all places`

MVP has no batch-default editor. New saves are Wanna with place visibility `self`; the destination list uses visibility `stealth` and the sanitized source name. People can change status, rating, place visibility, or list visibility after success through existing surfaces. This keeps the migration promise to one required decision after resolution.

#### 4. Commit

One tap initiates the batch. The UI reports progress without requiring individual input.

- Commit the set of ready new items plus reconciled exact duplicates. Each item uses a stable operation ID and canonical request hash.
- Preserve existing personal data on duplicates.
- Add both new and existing saved places to the private source-named rec.me list.
- Retry transient failures automatically within a bounded policy.
- Allow the user to leave and resume.

#### 5. Success

Lead with received value:

> **34 places are on your map**
> We made a private LA Spots list. Add ratings whenever you want.

Primary action: `View on map`
Secondary action: `Open LA Spots`

`View on map` always opens Map with the destination list filter active, regardless of entry surface. `Open LA Spots` opens list detail. Keeping this deterministic makes the payoff and acceptance tests consistent.

If exceptions exist:

> `29 newly saved · 5 already saved · 3 need help`

The success action is never blocked by exceptions. `Review 3` is a secondary action and persists in the import inbox.

#### 6. Needs Help

Source-level failures and item-level exceptions are separate.

Source-level failure actions:

- Private/inaccessible/malformed link: `Paste a different link` or `Cancel import`.
- Provider outage or retryable network failure: `Try again` or `Cancel import`.
- Oversize list: explain the 100-item beta limit; never truncate or create a partial batch.

Only the following resolved-item cases require item-level attention:

- Multiple plausible place matches.
- No match.
- Provider or network failure after bounded retry.
- A conflict that cannot be reconciled without changing personal data.

Item actions are `Choose match`, `Search manually`, `Try again`, and `Skip`. A resolved exception commits through the same idempotent item contract and joins the original destination list. `Skip` is terminal unless the user explicitly reopens the item. Reviewing one exception must not undo or hide successful imports.

### Data and save semantics

For each resolved source item:

| Field | New place default | Existing save |
|---|---|---|
| Status | Wanna | Preserve existing |
| Rating | Null | Preserve existing |
| Visit date | Null | Preserve existing |
| Notes | Empty/null | Preserve existing |
| Visibility | Self/private | Preserve existing |
| rec.me list | Add to private source-named list | Add membership only |
| Source provenance | Google Maps batch + source fingerprint | Associate import result without overwriting personal fields |

Place identity is exact only when the source provider ID is already mapped to a canonical rec.me place or the resolver returns the same stable provider identity. Name/address/coordinate similarity alone never qualifies as an exact duplicate; those candidates go to Needs Help rather than risk attaching the wrong venue.

Normalize a destination name by applying Unicode NFC normalization, removing control characters and line breaks, collapsing whitespace, and trimming. An empty result becomes `Google Maps Import`. The final name, including any suffix, must fit the existing 96-character schema maximum without splitting a grapheme. For a collision, reserve suffix length first, truncate the source portion to the remaining budget, and use `Source Name — Google Maps`, followed deterministically by `Source Name — Google Maps 2`, and so on.

### Durable ownership and contracts

The authenticated server-backed import repository is the source of truth. The minimum domain contract is:

```text
GoogleImportBatch
  id, owner_user_id, source_list_key_hash, source_display_name
  entry_context, destination_list_id, destination_generation
  state, capability_version
  ready_new_count, exact_duplicate_count, needs_help_count
  newly_saved_count, existing_attached_count, skipped_count, failed_count
  created_at, confirmed_at, completed_at

GoogleImportItem
  id, batch_id, ordinal, source_item_key_hash, source_fingerprint
  normalized_candidate, resolved_place_id, match_kind, state
  commit_operation_id, canonical_request_hash, result_user_place_id
  attempt_count, next_attempt_at, coarse_error_code
```

Expected authenticated client contracts:

- `create_google_import_batch(public_list_url, client_request_id, entry_context) -> batch_id`
- `get_google_import_batch(batch_id) -> batch summary + paged item summaries`
- `confirm_google_import_batch(batch_id, confirmation_operation_id) -> accepted counts/state`
- `retry_google_import_source(batch_id)`
- `select_google_import_match(item_id, canonical_place_id, operation_id)`
- `retry_google_import_item(item_id)`
- `skip_google_import_item(item_id)`
- `reopen_google_import_item(item_id)`
- `replace_google_import_destination(batch_id, operation_id)`
- `cancel_google_import_batch(batch_id)`

The submitted URL is stored only as an application-layer-encrypted, owner-scoped source artifact so acquisition can retry. It is deleted 24 hours after source resolution succeeds, immediately on cancellation, or at a seven-day absolute expiry, whichever comes first. It is never retained in analytics or long-term batch metadata. Owner-facing RPCs derive the user from authenticated claims and never accept a caller-selected owner ID.

The client generates `client_request_id` and confirmation-operation UUIDs, persists them before sending, and reuses them on retry. A create request stores a canonical hash of normalized URL plus entry context. Replaying the same `client_request_id` and hash returns the existing batch; reusing it with a different URL or entry context returns `operation_conflict`.

The server derives two item operations:

- `save_operation_id = (batch_id, item_id, save_contract_version)` with a canonical hash covering canonical place ID, fixed status `wanna_go`, fixed place visibility `self`, and contract version.
- `membership_operation_id = (batch_id, item_id, destination_generation, membership_contract_version)` with a canonical hash covering destination list ID, canonical place ID, destination generation, and contract version.

Canonical hashes use sorted-key canonical JSON. Reusing either operation ID with a different hash is a hard conflict. Splitting the operations lets destination repair attach an existing successful save to a replacement list without recreating or mutating the personal save.

Enumerated states and match types:

```text
BatchState = acquiring | resolving | ready_to_confirm
  | destination_setup_failed | committing | completed
  | completed_with_exceptions | destination_deleted
  | needs_source_help | cancelled | cancelled_partial

ItemState = queued | resolving | ready_new | exact_duplicate
  | needs_help | committing | committed_new | committed_existing
  | failed_retryable | failed_terminal | skipped | cancelled

MatchKind = stable_provider_id | exact_canonical_id | ambiguous | none
```

`normalized_candidate` contains only the bounded resolver input: display name, coarse address, coordinates when supplied, provider ID/URL token when supplied, source ordinal, and parser version. Legal item transitions are `queued -> resolving -> ready_new|exact_duplicate|needs_help`, ready/duplicate/reopened items `-> committing -> committed_*|failed_retryable|failed_terminal`, `failed_retryable -> committing`, `needs_help -> ready_new|exact_duplicate|skipped`, and `skipped -> needs_help` only through reopen.

Mutation RPCs return:

```text
CommandResult
  outcome = accepted | idempotent_replay | operation_conflict
    | invalid_state | not_found | forbidden | rate_limited
  batch_state, item_state?, summary_counts, coarse_error_code?
```

### Commit and partial-failure semantics

1. Confirmation creates or resolves the destination `stealth` list before any item is claimable. If destination setup fails, zero items commit and the batch remains retryable at `destination_setup_failed`.
2. A worker claims items with bounded concurrency. One database transaction per item executes the personal-save operation, preserves existing personal fields, executes the current-generation membership operation, and records the import-item result.
3. If any part of that per-item transaction fails, that item's save/membership/result roll back together. Other item transactions continue.
4. An existing active membership is an idempotent success. A previously user-deleted membership is not silently restored on re-import.
5. If the destination list is deleted during commit, the batch pauses at `destination_deleted`. `Create replacement list` increments `destination_generation`, makes a new unique `stealth` list, and runs a distinct idempotent membership-repair operation for already successful saves before resuming remaining items. `Stop import` keeps successful personal saves and cancels uncommitted items.
6. Cancellation stops new item claims. An in-flight item transaction may finish; completed saves remain and the final state is `cancelled_partial` when any item committed.

User-facing counts never collapse different outcomes. Confirmation reports `new places`, `already saved`, and `need help`. Completion reports `newly saved`, `already saved and added to list`, `need help`, and `skipped`.

### Re-import semantics

The normalized Google list identifier, not its display name or shortened URL, produces `source_list_key_hash`. A later import of the same source reuses the stored destination-list association and offers `Import new places` when unseen source item fingerprints exist.

- Source renames do not automatically rename a rec.me list the user may have edited.
- New source members append through the normal idempotent commit contract.
- Previously imported members remain unchanged.
- A place the user removed from the rec.me list is not silently re-added.
- Source removals never delete rec.me saves or list membership.

If the prior destination was deleted before a later import begins, confirmation explicitly offers `Create a new private list with N current places`. Accepting creates a new destination generation and attaches current source members, reusing existing personal saves without changing them. Nothing is recreated until this confirmation, so a prior deletion is never silently reversed.

### Retry and lifecycle policy

- Retry network timeouts, HTTP 408/429/5xx, and explicitly retryable provider/worker errors up to three automatic attempts with jittered 2-second, 8-second, and 30-second delays. A manual retry starts one new three-attempt cycle and is rate-limited server-side.
- Invalid/private URLs, authorization failures, the 100-item limit, no match, and ambiguous match are not automatically retried.
- Resolution and commit concurrency are each capped at four items per batch initially. Load tests at 50 and 100 items must verify provider throttling before Gate 2.
- Only one batch per owner may be in `committing`; additional imports may resolve and wait at confirmation.
- Multiple App Group shares remain in a seven-day FIFO queue and are presented one at a time. They are encrypted with iOS complete-file protection and contain only the minimum share envelope.
- On logout/account switch, bound server batches remain with their owner and disappear from the local UI. Unbound share envelopes require an explicit `Import to @handle` confirmation before binding and never transfer after binding.
- App termination does not lose state. Server workers may continue; client UI resumes by reading the durable batch. The product never relies on an ordinary foreground task surviving suspension.
- Server-side acquisition accepts only HTTPS Google Maps list URLs through a purpose-built fetcher: allowlisted Google host/path patterns, port 443 only, no embedded credentials, at most five redirects, host validation and DNS/IP checks on every redirect, rejection of private/loopback/link-local/reserved IPs, DNS rebinding protection, fixed connection/read timeouts, and the existing 20 MB response cap. It cannot fetch arbitrary caller-selected URLs.

### State model

The product state machine should be explicit and resumable:

```text
acquiring
  -> resolving
  -> ready_to_confirm -> committing
                            |-> completed
                            |-> completed_with_exceptions
                            |-> destination_deleted -> committing
                            |-> cancelled_partial

ready_to_confirm
  -> destination_setup_failed -> ready_to_confirm or cancelled

acquiring / resolving
  -> needs_source_help -> resolving or cancelled

resolving / committing
  -- retry metadata/backoff --> same batch state

completed_with_exceptions
  -> committing -> completed or completed_with_exceptions

committing
  -> cancelled when zero items committed
  -> cancelled_partial when one or more items committed

destination_deleted
  -> committing after replacement
  -> cancelled or cancelled_partial based on committed count

acquiring / resolving / ready_to_confirm
  -> cancelled
```

Auth/onboarding routing owns only the pending entry intent. The import repository owns batch progress, so process death or navigation does not erase a started import.

### Analytics and privacy

Add funnel events with counts and coarse states only:

- `google_import_entry_viewed` with entry context: ad, onboarding, add, share.
- `google_import_source_submitted` with method: paste or share.
- `google_import_resolution_completed` with ready-new/exact-duplicate/exception counts and duration bucket.
- `google_import_confirmed` with item count bucket; the MVP default is fixed.
- `google_import_commit_completed` with added/existing/failed counts and duration bucket.
- `google_import_success_action` with map, list, or review_exceptions.
- `google_import_explicitly_exited` with state and duration bucket.

Server analysis may infer abandonment when a ready batch remains unconfirmed for 24 hours; the client does not pretend it can emit an event when iOS kills the app. Resolution duration runs from accepted source submission to resolution terminal state. Commit duration runs from server acceptance of confirmation to commit terminal state and includes network/worker time.

Allowed coarse failure codes are `invalid_url`, `private_source`, `source_oversize`, `provider_unavailable`, `network_timeout`, `rate_limited`, `no_match`, `ambiguous_match`, `destination_deleted`, `commit_validation`, and `unknown`.

Do not send URLs, list names, place names, notes, coordinates, or raw error payloads.

## Success Criteria

### User experience

- A public list of 1–100 places can enter the flow; a 101-item list is rejected before staging with no truncation or partial import.
- A resolved batch requires exactly one decision to commit. Map/list buttons after completion are navigation actions, not import decisions.
- At least 90% of controlled 50-place TestFlight batches reach a commit terminal state within 60 seconds from server acceptance of confirmation, including network and worker time. The same test records 100-place behavior before Gate 2 rather than assuming it will meet the same budget.
- No ready item requires the normal per-place save sheet.
- No synthetic rating, visit date, or note is created.
- One failed or ambiguous item does not prevent successful places from appearing.
- Retrying or reopening the same batch does not duplicate saves or list memberships.
- Exact duplicates preserve all existing personal fields; fuzzy name/coordinate candidates never auto-attach.
- New saves use place visibility `self`; the destination list uses list visibility `stealth`.
- Completion copy distinguishes newly saved, already saved and attached, needs help, and skipped counts.
- Onboarding import success completes onboarding and opens the filtered Map; cancel/error continuation resumes the next normal onboarding step.
- VoiceOver, Dynamic Type, keyboard, offline, background/resume, cancellation, and small-phone layouts pass acceptance.

### Funnel validation

- At least 80% of users who reach a ready batch complete the batch commit during initial TestFlight validation.
- Measure entry-to-source-submitted, source-submitted-to-ready, ready-to-commit, and commit-to-map/list action separately for ad, onboarding, Add, and share.
- Record why imports fail so provider reliability can be separated from product abandonment without collecting place data.

### Technical validation

- Deep-link intent survives sign-in/onboarding and process recreation where the platform contract permits it.
- The batch commit is idempotent and has regression coverage for new save, existing save, save/membership transaction rollback, deleted destination, cancellation during commit, retry-hash conflict, re-import, user-removed membership, account switching, and cross-user isolation.
- Source fetch tests cover redirect allowlists, DNS rebinding, private/reserved IP rejection, credentials/ports, timeouts, redirect loops, and response-size limits.
- Hosted verification covers any new or changed iOS-called Supabase RPC, grants, `search_path`, ownership, anonymous access, and rollback safety.
- The public-list acquisition path has a server-controlled kill switch, remote copy, legal/provider review, redacted fixtures, and a live reliability canary before Gate 4.
- Load tests demonstrate bounded concurrency and record terminal-time distributions for 50- and 100-item batches before onboarding exposure.
