## Problem Statement

rec.me promises that trusted people's place memories become a searchable map, but its search surfaces currently implement different retrieval contracts:

- Map filters the already-visible corpus with one lowercased substring across a handful of fields, then performs an asynchronous MapKit search.
- Feed/Discover sends a submitted query through the Discover parser and filters by structured facets. A nonempty query with no recognized facet deliberately returns no places, even when the query names a place or text stored in a memory.
- People, Add, Lists, and Profile graph search each use separate matching and network behavior.

The result is that a query such as `Ryan coffee` can fail on Map because no single field contains the entire phrase, while free text such as a place name or note can fail in Discover because it is not a structured facet. Search behavior therefore depends on where the user started, not on the trusted memory graph they are trying to retrieve.

## Demand Evidence

- Joe reported directly that search “isn't working quite right” after using the current app and chose the shared-core approach for a trial implementation.
- REC-150 already established plain-language Discover search as an important user-facing behavior and shipped an LLM-backed structured-query path.
- The current product North Star explicitly depends on retrieving places through trusted people's memories.

This is strong founder and product-contract evidence, but not yet independent user-demand evidence. The implementation should therefore be a measured, reversible first slice rather than a backend search-platform migration.

## Status Quo

### Map

`MapScreen.visiblePlaces` applies the full normalized query as a substring to place name, category, locality, owner name/handle, note, and rating text. Tokens cannot match across different fields. MapKit typeahead and submitted search run asynchronously and can add external candidates after local filtering.

### Feed/Discover

`WanderStore.discover` waits for `parseDiscover`, applies the returned category/status/relationship/owner/area/tag/opinion filters to the visible corpus, and returns an empty place set when a nonempty query has no recognized facet. The parser cache and deterministic semantic normalizer already handle common structured concepts, but neither performs general text retrieval.

### Other surfaces

People search is prefix-oriented and permission-sensitive. Add is an external-place lookup. Lists and Profile graph have their own scoped behavior. These entity and workflow differences are real and should not be flattened into one universal service.

## Target User & Narrowest Wedge

The target user for this slice is a rec.me tester who remembers partial evidence about a saved place—who saved it, what kind of place it was, where it was, or what someone wrote—and searches from Map or Feed.

The narrowest useful wedge is one shared local retrieval core used by Map and Feed/Discover. It must support multi-token, cross-field matching and deterministic ranking over places the viewer is already allowed to see. It does not need embeddings, a new backend RPC, a universal entity result model, or migration of every search surface.

## Constraints

- Existing Supabase RLS and client visibility/blocking boundaries remain authoritative. The retrieval core only receives an already-visible candidate set.
- Local trusted-memory results must not add a network round trip.
- Map as-you-type search must remain responsive. Target p95 is under 50 ms for a representative in-memory corpus on the supported simulator class.
- Discover's LLM parser remains submit-only and useful for structured intent; it must not be treated as a general retrieval engine.
- MapKit remains the outside-world provider and must not outrank or obscure trusted memories.
- Swift 6 strict concurrency applies. The core should be a pure value-type API with no view, network, auth, or database dependency.
- No new dependency, schema, RPC, auth, visibility, or build-number change is required for the first slice.

## Premises

1. Search should answer from the viewer's trusted memory graph before searching the outside world.
2. Lexical retrieval is sufficient for the first slice because current failures are basic cross-field recall and ranking failures, not semantic-embedding failures.
3. “One platform” should mean shared place-query normalization, document construction, matching, ranking, and evidence—not one service that owns every entity and surface.
4. Surface orchestration belongs outside the core: Map decides when to request MapKit; Discover decides when to request structured LLM interpretation; People retains its own privacy-aware lookup.
5. The existing visible-place projection is the correct privacy boundary for local retrieval.

## Approaches Considered

### Approach A: Patch each surface

Add tokenized matching directly to Map and a lexical fallback directly to `WanderStore.discover`.

- Effort: Small
- Risk: Low immediately, high drift risk
- Advantage: Smallest initial diff.
- Cost: Duplicates normalization, field coverage, weights, and future bug fixes. Search semantics will diverge again.

### Approach B: Shared trusted-place core with adapters — chosen

Add a pure shared retrieval module and let Map and Feed/Discover compose it with their existing orchestration.

- Effort: Medium
- Risk: Low to medium
- Advantage: One place for query normalization, multi-field token coverage, ranking, and match evidence; no forced UI or provider unification.
- Cost: Requires a deliberate API boundary and adapter tests.

### Approach C: Universal search platform

Create one pipeline and result model spanning trusted places, people, MapKit results, lists, and future entities.

- Effort: Large
- Risk: High
- Advantage: One conceptual entry point.
- Cost: Erases important privacy, latency, and workflow differences; creates a large abstraction before the product has enough evidence to define it correctly.

## Recommended Approach

Implement Approach B as a small retrieval kernel plus surface-owned adapters.

### Shared core

Create a module under `Wander/Services/` with three concepts:

1. `TrustedPlaceSearchQuery`
   - Stores the original text, a folded normalized phrase, and meaningful tokens.
   - Removes punctuation, possessive suffixes, and this exact v1 low-information-word set: `a`, `an`, `and`, `at`, `find`, `for`, `give`, `in`, `me`, `of`, `or`, `place`, `places`, `please`, `show`, `spot`, `spots`, `that`, `the`, `to`, and `with`. Words outside this versioned set remain meaningful until deliberately added with tests.
   - Does not silently discard semantic words such as `favorite`. Discover may consume `favorite` only when its parser has produced the corresponding hard opinion filter. Map has no structured planner in this slice, so `favorite` remains a required lexical term and matches explicit note/label/attribute evidence; it does not silently broaden to every coffee place or infer a rating filter.
   - Provides a small, explicit alias table for known vocabulary equivalence such as `cafe`/`coffee` and `work`/`working`; no general fuzzy-edit-distance or embedding layer in this slice.
   - Separates `requiredTokens` from `scoringTokens`. Map has no structured planner, so every meaningful token is required. Discover may mark tokens or phrases as consumed by a hard structured filter; consumed terms may still add ranking evidence but are not required to match the raw document text again.

2. `TrustedPlaceSearchDocument`
   - Is derived from one `VisiblePlace`.
   - Indexes separately weighted fields: canonical place name; owner display name and handle; effective category/subcategory/cuisine; locality and address; note; personal labels; and structured attribute values.
   - Contains only display-safe data already present on the visible-place projection.

3. `TrustedPlaceSearchMatch`
   - Returns the original `VisiblePlace`, a deterministic score, and field-level evidence.
   - Requires every `requiredToken` to be covered somewhere in the document. Consumed structured terms remain optional `scoringTokens`. This allows `Ryan coffee` to match owner plus category without turning the query into a broad OR search, while a parsed phrase such as `people I follow` does not become an impossible lexical requirement.
   - Sorts by score, then saved-memory recency, then stable user-place ID so repeated runs are deterministic.

Initial ranking order:

1. Exact or prefix place-name phrase.
2. Place-name token coverage.
3. Exact/prefix owner name or handle.
4. Effective category, subcategory, or cuisine.
5. Locality/address.
6. Notes, personal labels, and structured attributes.
7. Stable recency tie-break after textual relevance.

The weights are implementation constants tested through relative-order assertions. Product code must not expose arbitrary numeric scores to users.

### Map adapter

- Build results synchronously from `baseVisiblePlaces` whenever the query changes.
- Replace the current full-string substring predicate with shared-core matches.
- Route saved-place typeahead through the same shared-core matches and ranking. The Map adapter still owns grouping, the three-saved-suggestion cap, current-user presentation, and the later MapKit append.
- Preserve Map's filter selections before retrieval.
- Continue grouping matched rows into map pins after ranking/filtering.
- Keep MapKit typeahead and submitted search asynchronous and revision/cancellation guarded.
- Treat external candidates as secondary: select a trusted match first when one exists and describe MapKit candidates as additional outside-map results.

### Feed/Discover adapter

- Add a synchronous `WanderStore.searchTrustedPlaces(query:scope:)` entry point that returns lexical matches, evidence, and elapsed time from the scope's already-visible places.
- On submit, increment a screen-owned `searchRevision`, cancel the previous refinement task, call the synchronous entry point, and publish those cards immediately without waiting for the remote parser.
- Continue `parseDiscover` asynchronously. When it completes for the current query revision, apply its structured filters as hard constraints and reuse the shared core for residual lexical ranking.
- Build a small Discover adapter plan that marks category, status, relationship, owner, area, tag, and opinion phrases satisfied by structured filters as consumed. This prevents phrases such as `people I follow` or `wanna go` from becoming impossible lexical requirements while keeping any unmatched place-name, note, or label terms required.
- Phrase consumption is deterministic: normalize the raw query with the shared tokenizer; generate candidate phrases from exact normalized filter values plus explicit product lexicons for category aliases, status, relationship, opinion, and common area abbreviations; sort candidates by descending token length then lexicographically; consume non-overlapping literal spans longest-first. Owner possessives normalize to the exact owner token. If an inferred filter has no literal or declared-alias span in the query, consume nothing for that filter. Never guess a span or consume the whole query; unmatched tokens remain required lexical evidence.
- If the parser recognizes no facet, keep the lexical results instead of forcing an empty result set.
- If the parser recognizes facets, structured filters narrow the immediate result set. Shared textual relevance orders the refined set unless `DiscoverFilters.sort` requests an explicit product sort such as owner rating; an explicit structured sort remains primary and textual score becomes its deterministic tie-break.
- The refinement task captures the revision and normalized query. It may publish only when both still match; cancellation or a stale completion is discarded.
- While refinement is pending, keep any immediate local cards visible and show a non-blocking interpreting state. If the immediate set is empty, retain the current loading treatment until refinement settles. Parser failure keeps the immediate local set and ends the interpreting state.
- Emit one submission event, then a local-result event immediately after the synchronous pass, and a structured-refinement event when the current parser result lands. Events include result count, facet count/source where applicable, and a coarse latency bucket; they never include raw query or memory content.
- Emit a privacy-safe result-selection event with `surface` (`map` or `discover`), `provider` (`trusted` or `mapkit`), `stage` (`immediate`, `refined`, or `external`), and rank bucket (`1`, `2_3`, or `4_plus`). Do not include raw query, place ID/name, owner, coordinates, or memory content.
- Preserve current parser caching, unsupported-concept messaging, evidence rows, cancellation, and stale-response protection.
- Do not surface People results inside the Places result list in this slice. Correct the place-search copy if it still promises people results.

### What remains separate

- `discoverMembers` and profile search: different entity, minimum-length rules, privacy semantics, and remote repository.
- MapKit search: outside-world provider with network latency and different add/save actions.
- Add: MapKit-first because its job is creating a place not already in the memory graph.
- Lists and Profile graph: scoped adapters to migrate after Map/Feed behavior is validated.

## Edge Cases

- Empty or punctuation-only query returns the input candidate order and does not call MapKit or the LLM by itself.
- A query containing only ignored intent words does not return every place; the adapter treats it as insufficient lexical evidence and relies on recognized structured filters or an empty state.
- A structured query whose words are fully consumed by hard filters may return the filtered candidate set even when no residual lexical token remains; its existing structured sort contract remains authoritative.
- Diacritics and case differences normalize consistently.
- Tokens may match different fields on the same memory but may not be assembled across different places.
- Blocked, private, or otherwise invisible rows never reach the core.
- Duplicate saves remain distinct retrieval matches until the surface's existing grouping layer combines them.
- Cancelled or stale parser/MapKit completions cannot replace results for a newer query.
- External MapKit failure leaves trusted-memory results intact.
- Searchable attribute decoding ignores malformed JSON rather than failing the query.

## Success Criteria

- `Ryan coffee` matches a Ryan-owned coffee memory even though no single field contains the full phrase.
- A distinctive place-name or note query with no recognized Discover facet returns matching visible memories rather than an automatic empty state.
- Given the same `TrustedPlaceSearchQuery` plan and candidate set, the shared core produces identical scores and ordering for Map and Feed/Discover. Surface hard filters, grouping, caps, and explicit structured sorts may intentionally change the final presentation.
- Exact/prefix name matches outrank owner/category-only matches; owner/category matches outrank note-only matches.
- Unknown text with no token coverage returns no places rather than the whole corpus.
- On Map, `favorite coffee` requires literal favorite evidence plus coffee evidence; it does not invoke Discover semantics or return every coffee result.
- Map trusted results update synchronously; MapKit continues asynchronously and cannot erase trusted results on failure.
- Discover can show local matches before remote structured interpretation completes, with stale responses ignored.
- Representative local retrieval p95 remains below 50 ms after a warm-up pass.
- Existing Discover structured-query, visibility, blocking, MapKit cancellation, and navigation tests remain green.

## Validation Plan

- Add focused unit tests for normalization, possessives, aliases, cross-field token coverage, no-match behavior, deterministic ordering, malformed attributes, and ranking evidence.
- Add planner tests for longest-first overlapping phrases, declared aliases, owner possessives, queries fully consumed by structured filters, and inferred filters with no literal/alias span (which must conservatively consume nothing).
- Add integration tests proving Map filtering, Map saved-place typeahead, and Discover's immediate lexical stage reuse identical core ordering before their documented grouping, caps, or structured refinement.
- Replace the current unknown-query Discover contract with two cases: matching free text returns memories; genuinely unknown text returns empty.
- Preserve structured Discover tests including exact owner resolution and favorite semantics.
- Add a reproducible focused performance test: 1,000 deterministic `VisiblePlace` candidates with notes and structured attributes; one four-token cross-field query; full document projection plus ranking inside the timed region; five warm-up runs followed by 30 measured runs using `ContinuousClock`; Debug XCTest on the standard iPhone 16 Plus / iOS 18.6 simulator destination with `-jobs 1`; assert measured p95 under 50 ms and print the host model plus all samples on failure.
- Run focused search/parser/store/navigation suites, then the full iPhone 16 Plus / iOS 18.6 test suite and generic Simulator build.
- Run `git diff --check` and inspect the generated Xcode project after XcodeGen.
- Perform focused visual QA on the current large and small iPhone targets only if presentation or copy changes.

## Rollout and Observability

- Ship through the existing iOS branch/PR/TestFlight process; no backend deployment is part of this slice.
- Track local result count, structured-refined result count, zero-result outcome, and coarse latency bucket without logging raw query text or place-memory content.
- Track privacy-safe result selection by surface, trusted-vs-MapKit provider, refinement stage, and rank bucket. Compare zero-result rate and trusted-result selection behavior before expanding the core to Lists/Add.
- If the visible corpus grows enough that local scan p95 approaches 50 ms, preserve the same query/result contract behind an RLS-safe backend full-text/trigram RPC. Do not introduce embeddings until lexical retrieval failure is demonstrated with real queries.

## Open Questions

None block the first slice. The following are deliberate follow-ups:

- Whether Lists should show trusted matches and MapKit matches in separate sections.
- Whether a future unified search UI should show People as a sibling result section.
- What corpus size should trigger a backend indexed-search migration.
- Whether query-level synonyms should remain a small product vocabulary or move to a server-managed configuration.
