# REC-95 List Map Engineering Plan

**Linear:** REC-95
**Date:** 2026-07-18
**Scope:** List detail map preview, full-screen list map, synchronized place rail, and list-map place presentation
**Companion design review:** `docs/reviews/2026-07-18-rec-95-list-map-design-review.md`

## Objective

Make the map preview in list detail and the full-screen list map feel like one continuous, trustworthy flow:

- The list-detail preview shows the actual mapped places instead of a decorative approximation.
- The full-screen map keeps a compact, persistent place rail visible while the user explores.
- A pin and its rail tile share one focus state.
- A rail-tile tap opens the production place profile on the first tap.
- Production list places retain their canonical place, save, ownership, and social context all the way into the profile.
- List-map pins reuse the same ownership and Been/Wanna go outline vocabulary as the main map.
- Compact media follows REC-93: an eligible local visit photo when available, otherwise a category fallback, with no compact-surface Google/place-photo fetch.

The implementation remains native SwiftUI/MapKit and does not change global Map behavior.

## Current Failure Modes

The current flow has several architectural and interaction problems that visual polish alone will not solve:

1. `ListMapPreview` is a static gradient with arbitrary `pinPosition` values. It does not communicate the list's real geography.
2. `ListMapFullScreen` swaps the horizontal rail for an intermediate `PlaceProfileMapSurface` when a pin is selected. The map-to-place flow therefore changes shape, and a pin selection creates an unnecessary extra state before the full profile.
3. `ListPlaceMock.init(visiblePlace:)` reduces a production `VisiblePlace` to display strings and coordinates.
4. `PlaceSheetPlace.init(listPlace:)` then reconstructs a synthetic place with a generated id, hard-coded Los Angeles metadata, a synthetic owner, empty save arrays, and a hard-coded current user id. This loses the canonical identity needed for correct profile data, photo lookup, status, and social context.
5. List map markers infer ownership from status. Ownership and Been/Wanna go are independent concepts, so a current-user Wanna go or a social Been save can be colored incorrectly.
6. The full-screen header and rail consume too much map area, particularly on small phones, and the current nested surfaces obscure hierarchy.
7. The list's cached item count can differ from resolved or mappable places, but the UI currently reports only `places.count` without explaining that distinction.

## Non-Goals

- Redesigning the global Map tab.
- Implementing Lists-home photo covers from REC-93.
- Fetching remote visit-photo thumbnails per tile.
- Adding a new Supabase RPC, schema field, RLS policy, persistence model, or sync behavior.
- Treating the store's global `lastRemoteError` as a list-map error. That value is not scoped to this surface and could show an unrelated failure.
- Adding collaboration, add-place, or list-editing behavior.
- Resolving the social-save synchronization limitation tracked separately by REC-103.

## Data and Presentation Architecture

### 1. Keep one list-map presentation projection

`PlaceListMock` remains the private Lists presentation model for this change, but its production initializer must build richer `ListPlaceMock` values with store context rather than calling the lossy `ListPlaceMock.init(visiblePlace:)` projection.

For every resolved list item, the presentation projection should retain:

- The canonical `VisiblePlace`.
- The canonical `PlaceSheetPlace`, constructed with `PlaceSheetPlace.init(visiblePlace:)`.
- All privacy-filtered visible saves that match the place through `VisiblePlaceGrouping`.
- The current user's matching saves used by the place-profile presentation.
- The active `currentUserID`.
- Save states required by `MapPinOutlineBuilder`.
- An optional eligible local visit photo.
- Existing compact display values such as name, category, locality, note, status, coordinate, emoji, and tint.

Static demo fixtures may continue to use synthetic values, but they must enter through an explicit fixture initializer. Production values must never be reconstructed from display strings.

Suggested private shape:

```swift
private struct ListPlaceMock: Identifiable {
    // Compact presentation values used by list/map UI.
    let id: String
    let name: String
    let category: String
    let metadata: String
    let coordinate: CLLocationCoordinate2D

    // Canonical profile and social context.
    let profilePlace: PlaceSheetPlace
    let saves: [PlaceSaveSummary]
    let tasteSaves: [PlaceSaveSummary]
    let currentUserID: String

    // Shared pin and compact-media presentation.
    let outlines: [MapPinOutline]
    let compactVisitPhotoAssetRef: String?
}
```

The exact stored fields may differ to preserve existing call sites, but the invariants are:

- `profilePlace.id` is the real place id for production data.
- Profile navigation receives the matching save arrays and real current user id.
- Compact UI does not need to query the store during rendering.
- Fixture and production projections are visibly separate in code.

### 2. Group saves once during projection

For each list `VisiblePlace`, derive the matching privacy-filtered save group from `store.visiblePlaces()` using `VisiblePlaceGrouping.matches` or the existing group helpers. Convert matching values into the same `PlaceSaveSummary` representation used by the main map and place profile.

Do this while building `PlaceListMock`, not independently in every marker or tile. This gives pins, tiles, and profiles the same social truth and avoids repeated filtering during SwiftUI body evaluation.

### 3. Reuse REC-99 outline semantics

Build `[MapPinSaveState]` from the matching save group:

- `.currentUser` when the save owner id equals `store.currentUser.id`.
- `.social` otherwise.
- Preserve each save's actual `.been` or `.wannaGo` status.

Pass those states through `MapPinOutlineBuilder.outlines(for:)`. The list preview and full-screen marker then render the resulting outline strokes. They must not derive owner color from `PlaceStatus`.

This plan assumes the approved REC-99 outline primitives are available on the branch. If REC-99 has not landed on `main`, incorporate its shared pin primitives without reimplementing an alternate list-only vocabulary. Keep the selection treatment separate from ownership/status outlines: selection may add scale, shadow, or an outer ink focus ring, but it must not replace the semantic outlines.

### 4. Add the REC-93 compact-photo seam without a new remote contract

For production list places, resolve only an already-available, viewer-eligible local visit photo:

1. Ask the store for `firstVisitPhoto(forPlaceID:)` using the canonical place id.
2. Retain only its optional `localAssetRef` in the list presentation model.
3. Decode that local asset reference in the compact media view.
4. Keep the category tile in place until a valid local image is decoded.
5. Fall back immediately to the category tile for `nil`, missing, unreadable, loading, or failed local assets.

The compact rail media frame is 62 points, as locked in REC-93. It must not call the Google Places photo API, trigger per-tile RPCs, or fetch a remote full-size profile image. When REC-93 gains a batch-delivered viewer-visible thumbnail contract, it can feed this same optional presentation seam.

Use a short 180–240 ms photo crossfade when a local image becomes available. Do not show a skeleton for a 62-point tile; the category fallback is the stable loading, error, and offline presentation.

## Count Semantics

Expose three distinct private counts on `PlaceListMock`:

- `totalItemCount`: the list's authoritative or cached item count (`cachedItemCount`, falling back to resolved items).
- `resolvedPlaceCount`: list items resolved into visible place presentation values.
- `mappedPlaceCount`: resolved values with valid coordinates that can render as annotations.

Use them deliberately:

- List detail retains the existing list item count language.
- The map preview and full-screen map use `mappedPlaceCount` for direct map claims.
- If `totalItemCount > mappedPlaceCount`, use neutral copy such as “3 mapped of 5 places” rather than implying data was deleted.
- Do not fabricate coordinates for a production place merely to make the counts match.
- Static fixture coordinates remain valid only in fixture initializers.

This distinction makes partial cached/offline states honest without introducing a new network contract.

## UI State Model

Introduce a small, pure list-map presentation state rather than reading unrelated global store state:

```swift
private enum ListMapContentState: Equatable {
    case empty
    case unresolved(total: Int)
    case partial(mapped: Int, total: Int)
    case mapped(count: Int)
}
```

Derive it only from `totalItemCount`, `resolvedPlaceCount`, and `mappedPlaceCount`.

- `empty`: zero total items. Keep the map background and show a compact “No places to map yet” bottom surface.
- `unresolved`: a nonzero cached total exists but no place currently has usable map data. Show a compact neutral status surface such as “Places are not available yet.” Do not label it a network error without scoped evidence.
- `partial`: render the available pins and rail, and report the mapped/total count.
- `mapped`: render normal map and rail behavior.

Loading, explicit request failure, and offline messaging require a list-scoped repository state. No such state is added in this PR. A follow-up should thread a scoped loading/error/offline value through the list repository and store, then extend `ListMapContentState`. Do not wire this surface to `lastRemoteError`, because it can describe an unrelated background operation.

The REC-93 category fallback still guarantees that photo loading/error/offline never collapses or blocks a tile.

## Interaction State and Data Flow

Use one stable identifier for focus:

```text
pin tap ───────────────┐
                      v
                focusedPlaceID
                      ^
rail scroll position ─┘

rail tile tap ──> profilePlace ──> full production place profile
```

### Full-screen map behavior

1. `focusedPlaceID` starts with the requested initial place id, or the first mapped place when appropriate.
2. Pin tap sets `focusedPlaceID`.
3. The horizontal rail uses `ScrollViewReader` or iOS 17 scroll-position APIs to bring that tile into view.
4. User-driven rail scrolling updates `focusedPlaceID` when a new tile settles.
5. Focused marker receives only the visual focus treatment; semantic outlines stay unchanged.
6. The rail remains visible while focus changes.
7. A rail-tile tap sets the profile destination directly. There is no intermediate `PlaceProfileMapSurface`.
8. Back from the profile returns to the map with the same camera and focused tile.
9. Closing the map returns to list detail.

Avoid feedback loops between programmatic scrolling and scroll-position changes by making `focusedPlaceID` the sole source of truth and ignoring no-op assignments.

### List-detail preview behavior

- Render a real, non-interactive MapKit map using the same `mapRegion`.
- Render only valid mapped places.
- Reuse the same marker semantics at preview scale.
- Let the map body and separate action row open the full-screen map while
  reserving a narrow bottom strip for MapKit’s native Apple Maps/Legal control.
- Disable pan and zoom without disabling or covering native attribution.
- Preserve the current full-screen transition mechanism unless testing exposes a navigation bug.

## Layout Plan

### List-detail preview

- Real muted MapKit map, approximately the existing visual height.
- No place-name annotation labels; labels are exposed to accessibility, not drawn on top of the preview.
- Separate 52pt bottom action row containing “View map,” mapped-count copy, and
  a chevron; this keeps attribution legible inside the 168pt map canvas.
- Honest empty/unresolved treatment inside the same frame.
- Rounded rectangle and border/shadow tokens from `WanderTheme`.

### Full-screen header

- A standalone 44×44 close button.
- A compact adjacent title/count surface rather than one full-width capsule.
- Up to two title lines at standard sizes and three at accessibility sizes.
- Count stays readable and uses mapped/total language where needed.
- Respect top safe area without covering more geography than necessary.

### Persistent bottom rail

- Use a safe-area-aware bottom inset/surface.
- Show one primary card and a partial next-card affordance.
- Avoid a large outer rounded container plus independently rounded nested cards.
- Each card has a 62×62 compact-media region, two-line place name, one-line coherent context, and an open affordance.
- Context order: ownership/social source, status, category/locality as space permits.
- Card height may grow for accessibility text sizes; do not shrink below legibility.
- The complete card is one button with a minimum 44-point target and an explicit “Open [place]” accessibility label.

## Deterministic QA Fixtures

Extend the existing `-WanderInitialTab lists` / `-WanderListsScenario` launch-state mechanism rather than adding an automated UI-test dependency. Keep fixture data local and deterministic.

Required scenarios:

- `mapEmpty`: `totalItemCount == 0`, no mapped places.
- `mapSingle`: one valid mapped place.
- `mapClustered`: several nearby coordinates that exercise marker overlap and focus.
- `mapDispersed`: geographically spread coordinates that exercise region fitting.
- `mapPartial`: cached total exceeds mapped count.
- `mapUnresolved`: cached nonzero total with no valid mapped place.
- `mapUnmapped`: one resolved place with invalid/sentinel coordinates; no fake
  pin, but its card remains openable from the rail.
- `mapLongNames`: long list and place names.
- `mapSelectedPlace`: opens with a deterministic focused marker and rail tile.
- `mapPlaceDetail`: opens the same canonical-style profile destination used from the rail.
- `mapLocalPhoto`: one deterministic local compact visit-photo asset if a stable fixture file can be bundled without adding production fetch behavior.

If a bundled local test image would create unrelated project/resource churn, validate the photo view with a focused unit/view model test and retain category fallback in screenshot fixtures. Remote photo behavior remains outside this issue.

## Test Plan

### Unit and contract tests

Add focused coverage for pure logic and production projection:

1. `MapRegionFitter`
   - No coordinates returns `nil`.
   - One coordinate receives the minimum span.
   - Clustered coordinates remain bounded with padding.
   - Dispersed coordinates include all extrema.
   - Invalid coordinates do not create annotations or distort the region.
2. List-map count state
   - Zero/zero derives `.empty`.
   - Nonzero total/zero mapped derives `.unresolved`.
   - Total greater than mapped derives `.partial`.
   - Equal nonzero values derive `.mapped`.
3. Production place projection
   - Retains canonical place/profile id.
   - Retains canonical locality/address/provider data needed by the profile.
   - Passes the real current user id.
   - Includes all matching privacy-filtered save summaries.
   - Does not synthesize a Los Angeles location or a “You” owner for social production data.
4. Outline state projection
   - Current-user Wanna go remains current-user color and dashed.
   - Social Been remains social color and solid.
   - Mixed ownership produces the REC-99 split outline ordering.
5. Compact photo
   - Eligible local visit photo projects into the optional seam.
   - Missing/unreadable photo resolves to category fallback.
   - No test or production compact path invokes the remote provider-photo loader.
6. Navigation contract
   - Selecting a rail tile produces the full profile destination immediately.
   - Focus changes do not create a separate intermediate profile-surface state.

Prefer extracting private, deterministic helpers into testable internal types only where needed; do not broaden product API visibility solely for tests.

## Implementation Sequence

1. Integrate or reuse the approved REC-99 shared outline primitives.
2. Add count/state helpers and unit tests.
3. Refactor the production `PlaceListMock`/`ListPlaceMock` projection to retain canonical profile and save context.
4. Add the optional REC-93 local-photo presentation seam and category fallback.
5. Replace the decorative preview with a non-interactive MapKit preview.
6. Refactor `ListMapFullScreen` around `focusedPlaceID`, persistent rail, and direct profile navigation.
7. Restyle header, markers, and rail for small-phone and Dynamic Type behavior.
8. Add deterministic launch scenarios and focused regression tests.
9. Run the full build/test suite and visual QA matrix.
10. Record screenshots, validation, known gaps, and follow-up needs in the agent log and Linear issue.

## Rollout and Risk

The feature is local UI/presentation work over existing repository data, so no migration, hosted smoke test, or backend rollout is required.

Primary risks:

- **REC-99 overlap:** Lists map pin code is already touched by REC-99. Reuse its primitives and integrate intentionally; do not fork the semantic implementation.
- **Identity regression:** A production profile must receive the canonical place and matching saves. Tests should fail if synthetic reconstruction returns.
- **Scroll synchronization loops:** Keep one focus id and test pin-to-rail and rail-to-pin transitions repeatedly.
- **Partial cache ambiguity:** Report total and mapped counts separately; do not claim an unrelated global error.
- **Photo policy drift:** Compact media must remain local/eligible-or-fallback until REC-93 supplies a batch remote-thumbnail contract.
- **Small-phone crowding:** Validate the real rail and header on the smaller target, not only previews.
- **MapKit attribution:** Reserve actual map layout space; never cover or
  disable Apple Maps/Legal controls with a CTA or rail overlay.

## Completion Criteria

REC-95 is implementation-complete when:

- The list-detail map uses real MapKit geography and production coordinates.
- The preview and full-screen markers share REC-99 ownership/status semantics.
- Pin selection and rail focus remain synchronized without replacing the rail.
- The first rail-tile tap opens the full place profile.
- Production navigation preserves canonical place identity, real current user, save summaries, and social context.
- Compact media uses an eligible local visit photo when available and category fallback otherwise, with no per-tile remote photo request.
- Total, resolved, and mapped counts produce honest empty/unresolved/partial/mapped UI.
- Deterministic fixture states cover 0, 1, clustered, dispersed, partial,
  unresolved, resolved-unmapped, long-name, and initial-focus behavior.
- Full tests pass and screenshots are reviewed on a current and smaller iPhone target, including Dynamic Type and safe areas.
- Any explicit network error/offline UI remains deferred to a follow-up with list-scoped repository state; this PR does not misuse `lastRemoteError`.
