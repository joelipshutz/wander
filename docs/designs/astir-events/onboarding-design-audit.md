# Astir Events — RSVP-to-ticket onboarding design audit

> Historical September 10 design study. The September 14 walkthrough supersedes conflicting details below: confirmation has an optional download offer; recognized confirmed guests manage RSVP and see the full guest list in App Clip/web without installing; name and username are required before entry/QR; map tap opens a collapsed card first; the invented recommendations detour is removed. This audit expands the onboarding paragraph in the [product draft](product-spec-draft.md) into screens and recovery states. All copy, screen grouping, back behavior, and contextual-prompt timing below are **proposed design**, not newly approved product behavior.

## Approved rules to preserve

- D14–D16: App Clip is the preferred no-install RSVP route; equivalent browser RSVP is the fallback. The full app must be publicly available before live Events. A supported phone and installed Astir are required for admission; browser RSVP is not browser admission. TestFlight is a separate testing path.
- D17/D19: Apple or Google identity plus a verified phone number before RSVP confirmation. Reuse a matching, actually verified number. Explain event-specific texts; future-event texts have a separate, optional, initially unchecked opt-in.
- D18: strongly prompt for a profile photo during app setup, but allow skipping. Missing photo cannot block RSVP, ticket access, or event check-in.
- Return from RSVP must preserve the event and reservation through shortened setup. General product education must not prevent reaching the ticket. Exact name/username handling and contextual permission timing remain proposals in the product draft.
- Pending approval, waitlist, offered, confirmed, canceled, and admitted are different states. Only confirmed guests get the admission ticket. Admission is not the later event check-in.

**Highest-risk omission:** no agreed screen-level handoff currently carries a valid RSVP through fresh installation and the app-entry gate to its ticket. The proposal must work both when the guest reopens the event link and when they tap the newly installed app icon. A general-onboarding interruption at the door defeats the stated progression even if RSVP and QR screens work separately.

## Proposed screen sequence

Keep a compact event header—cover thumbnail, title, local date/time—through RSVP, setup, and recovery. It is the continuity anchor, not a second splash. Use at most three major elements above the fold: event context, the current task, and its action area. Browser/Clip variants preserve the same meaning and outcomes; exact platform implementation remains to be validated.

| Screen | Proposed content and primary action | Back / continuation behavior |
| --- | --- | --- |
| **1. Event detail** | Immersive event content, truthful face pile/count, prominent **RSVP** and Share. Before RSVP: “Entry requires Astir on a compatible iPhone. Your entry QR will be in the app.” Platform-specific device wording must match the released supported-device contract. | Closing returns to the source. A visible **Continue in browser** fallback keeps the same event when the Clip cannot open. A desktop visitor is not treated as an unsupported-phone owner. |
| **2. Access code, when required** | “Enter the event code.” One input; **Continue**. Missing/invalid: “That code didn’t work. Check it and try again.” A valid code is not confirmation. | Back to the same detail. Preserve previously completed identity steps. Existing valid confirmations/offers are not sent through this new-request gate again. |
| **3. RSVP identity** | Event context plus “Continue to RSVP.” **Continue with Apple** and **Continue with Google**, using their recognized controls. If already signed in, show a compact “Continuing as [name]” row and **Continue**, with **Switch account**. | Canceling the provider returns here without a red failure state. Back returns to detail/code and does not cancel an existing booking. Known returning guests use the account associated with the reservation. |
| **4. Name, phone, and texts** | Prefill a known name and phone; ask only for missing/corrected values. “We’ll text you confirmations, reminders, and important updates for this event.” Separate unchecked checkbox: “Text me about future Astir events.” Primary **Send code** for an unverified number. If matching verification is established, show “Phone verified” and the applicable **Confirm RSVP**, **Request RSVP**, or **Join waitlist** action. | Back preserves entered information for this account and event. Editing a phone removes the verified presentation until the new number is verified. Changing accounts clears the previous account’s private form content. |
| **5. SMS code** | “Verify your number” and masked destination; one accessible code field with autofill/paste. Primary **Verify and continue**. Secondary **Change number** and resend with an honest countdown. No statement that the spot is secured. | Back edits the number without losing the event. On success, re-evaluate current availability/approval and finish the intended request; do not assume a seat remained available during verification. An already-existing booking returns its current state. |
| **6. Reservation outcome** | Confirmed: “You’re on the list.” **Get Astir** or **Open Astir**; secondary **Add to calendar**. Pending: “Your request is with Astir.” Waitlist: “You’re on the waitlist.” Offered: deadline plus **Accept spot**. Status explains what happens next; pending/waitlisted/offered states show no entry QR. | Back opens event detail with the same status. The confirmation page stays usable after an App Store round trip; **Open Astir** and the original event link remain explicit return routes. Do not promise automatic continuation after installation. |
| **7. Full-app reservation recovery** | Validate the session, then load the signed-in account’s booking. Short loading copy: “Finding your RSVP…” No carousel, permission sequence, or general tour for a recognized event return. A signed-out return shows event-specific sign-in: “Sign in with the account you used to RSVP.” | If opened from the app icon without event context, provide **Already RSVPed? Sign in** from the signed-out entry. After sign-in, recover that account’s active reservations; if several exist, show Events for selection. If none exists, show an honest empty state and account/help actions—not an automatic new RSVP. |
| **8. Only missing profile identity** | When necessary: “A few details for your Astir profile.” Reuse saved name/handle; show only missing required fields, username availability, and **Continue to your event**. This is a proposed retained identity requirement, not a reason to repeat completed RSVP fields. | Back returns to the event/status context; it does not remove the reservation. Conflicts show beside the username, preserve other fields, and offer editing. Existing complete profiles skip this screen. |
| **9. Strong optional photo prompt** | For a first return without a photo: “Help people recognize you.” “Add a profile photo—you can do this later.” Primary **Add a photo**, with clearly visible **Skip for now**. After selection/crop: **Use photo**. Reuse an existing photo and skip the prompt. | Canceling the picker/crop returns to this prompt. Skipping continues immediately. Do not present the same prompt on every ticket reopen or foreground activation. If combined with screen 8, keep Skip independent of required identity validation. |
| **10. Ticket in Events** | Event title/date, confirmed status, guest name, scannable QR, “Show this at the door.” Secondary **Event details** and **Need help?** Keep private-home address reveal/expiry independent of ticket presentation. No upsell overlays the QR. | Back returns to Events. Reopening the event or its ticket returns directly here for an eligible existing guest. Pending, offered, canceled, or expired states route to their actual status instead; successful sign-in never upgrades eligibility. |

The confirmation screen should give a short install instruction: “Install Astir, then open this link again or sign in to find your RSVP.” Preserve this explicit recovery even if a seamless handoff is later proven reliable.

## Proposed recovery and returning-user variants

| Situation | Copy and primary action | State / back behavior |
| --- | --- | --- |
| Existing member, same valid account and verified matching phone | Skip duplicate sign-in, identity, SMS, and photo setup. **RSVP** or the current booking action. | Return to the selected event, not the generic home screen. A changed phone must be verified. |
| Provider authentication canceled | Return to provider choices; no error toast. | Retain event intent. No reservation is created or canceled by cancellation. |
| Provider failure or no adopted session | “Sign-in didn’t finish.” **Try again**; **Back to event**. | Other method is available only as an intentional identity choice. Do not imply it automatically recovers the same booking. |
| Provider needs additional verification | “Finish verifying your account to continue.” **Continue sign-in** when a supported continuation exists; otherwise **Get sign-in help**. | Preserve event/offer context. Do not label this SMS failure, restart signup as a new account, or display a confirmed ticket. Exact provider continuation is an engineering-validation dependency. |
| Wrong signed-in account | “This RSVP isn’t linked to this account.” **Switch account**; secondary **Get help**. | Do not reveal the other owner’s name/phone or transfer/merge the booking. Back returns to permitted event detail. After switching, discard previous-account tickets and drafts before rendering the new account. |
| Phone is stored but verification cannot be established | “Verify your number to finish your RSVP.” **Send code**. | Keep identity and event context; a string copied from an account is not a verified badge. |
| Incorrect/expired SMS or resend failure | “That code isn’t right” / “This code expired” / “We couldn’t send a code.” **Try again** or **Resend code**, with **Change number**. | Preserve other fields; explain any wait before resend. Never reset to the event discovery screen. The draft’s 60-second resend proposal must match actual provider behavior. |
| Request response lost or availability changed | “Checking your RSVP…” then its authoritative status; **Retry** only if resolution fails. | Do not show “You’re in” on an unknown result. Show waitlist/pending if that is the resolved outcome; repeated taps must not create another booking. |
| Profile save/username conflict | “That username is taken” beside the field, or “We couldn’t save your profile.” **Try again**. | Retain name and optional photo selection; never cancel or hide the existence of the RSVP. Help stays accessible if this blocks ticket setup. |
| Photo loading/upload failure | “Your photo didn’t upload.” **Try again**, **Choose another**, and **Continue without photo**. | No false saved success; optional-photo failure cannot block ticket access. After proceeding, use the existing avatar/initials and allow later Profile editing. |
| Install interrupted / app opened independently | Confirmation keeps **Get Astir** / **Open Astir**. In the app, **Already RSVPed? Sign in** recovers bookings by authenticated account. | Do not rely on the App Store preserving the event URL. Never ask the guest to RSVP again just to recover a ticket. |
| Session/profile network failure | “We couldn’t load your RSVP.” **Try again** and **Get help**. | Keep non-sensitive event context. Do not treat cached identity as authenticated. A permitted cached ticket/offline display needs its own verified eligibility rules; the existing offline-map option is not admission proof. |
| QR cannot load for a confirmed installed-app guest | “Your entry code couldn’t load.” **Retry**; “Already at the door? Ask the Astir team to look up your confirmed booking.” | This is the approved D25 staff fallback. It does not grant a no-app/unsupported-device exception or let the guest self-record admission. |

## Later contextual prompts — proposed, never before the ticket

Offer the feature on its relevant surface before presenting a native permission primer. Declining to start an optional feature leaves the current experience usable. Once a native-permission primer is opened, use the design system’s neutral **Continue** action; after system denial, explain recovery and permit returning to the original surface.

| Context | Proposed invitation / action | Denied or declined result |
| --- | --- | --- |
| Guest uses Map’s nearby/location control | “Find places near you.” **Continue** then the native location request, only if needed. | Keep map pan/search and Events usable. **Open Settings** is optional recovery. Event venue lookup and the QR do not require device location. |
| Guest explicitly chooses Find friends | “Find friends already on Astir.” **Continue** then the contacts request. Friend suggestions follow that choice. | Keep username search available; do not send contacts/messages. No automatic detour from ticket or recap into the social setup. |
| Guest chooses event-notification setup after the ticket has been reached | A quiet event-detail/Events action **Turn on notifications**, then the existing neutral primer and native prompt. | Ticket/RSVP stay usable and agreed SMS behavior stays separate. Do not confuse push permission with future-event text consent. No alert stack on first ticket display. |
| Guest chooses Add photo | Open the supported photo picker from that action; crop/preview has Cancel and Use photo. | Cancel/no selection preserves the form. Do not introduce a broad photo-permission onboarding step. |
| Guest later explores the map/product | Contextual help for the chosen feature; no replay of the entire first-run carousel or forced tour. | Dismissed help remains dismissed for this account. Deferred prompts are not falsely marked granted or completed. |

## Visual and accessibility application

Follow [DESIGN.md:21](https://github.com/joelipshutz/wander/blob/f8d258e869503a28d70518a050dff36a344134c6/DESIGN.md#L21): warm paper/ink, adaptive dark appearance, coral action accent, editorial serif titles, Avenir Next controls/body, and restrained individual glass elements. Its older rec.me name, four-tab list, and mandatory general carousel conflict with the newer user direction/current code; use Astir and the approved event-first progression rather than reviving those older product rules. The basic authenticated-session boundary remains intact.

Use persistent field labels and inline errors, at least 44-point targets, visible keyboard-safe primary/secondary actions, Dynamic Type wrapping, and VoiceOver announcement of changed RSVP states. The optional photo skip must be as reachable with VoiceOver as Add photo. Code entry is one accessible field, not six separately navigated unlabeled boxes. Never convey pending/confirmed/error only by color. Do not use decorative auto-advancing slides or loading animations between RSVP and ticket.

## Design acceptance checks

1. Fresh Clip RSVP → SMS verification → confirmation → install → signed-in reservation recovery → only missing profile details → skip photo → correct event QR, without location/contacts/notifications/tour interruption.
2. Browser fallback and app-icon launch recover the same reservation; opening a generic app-store page does not lose the only recovery path.
3. Existing valid member skips repeated fields; pending/waitlisted/offered users see truthful status rather than a ticket.
4. Provider cancel, extra verification, wrong account, changed phone, expired code, failed profile save, and failed photo upload each retain the event and expose one clear recovery action.
5. Reopen/foreground does not repeatedly request optional photo or general onboarding. Account switching does not retain another person’s ticket or private form content.
6. Later permission denial cannot invalidate the RSVP, hide the ticket, or require restarting setup. A stored phone string never displays as verified without verification evidence.

The specific screen proposals above are ready for design review. App Clip authentication, installation handoff, provider continuation, and offline ticket behavior still need engineering validation; this audit does not claim they already work.
