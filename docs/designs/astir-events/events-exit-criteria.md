# Astir Events — planned engineering exit criteria

Updated September 15, 2026. **This is an acceptance-test specification. These tests are not implemented, run, or passed.** It describes the fixtures, actions, and observable results the engineering plan must implement and verify. Wireframe rendering checks are separate evidence and cannot satisfy backend, identity, delivery, privacy, or admission acceptance.

The companion [event-link decision model](event-link-decision-model.json) defines one canonical event link, independent surface/identity/booking state, and action gates. The current [requirements ledger](audit/requirements.md), original decisions D1–D35, and newer recordings remain the source of product authority. Cases marked **Proposed** preserve concrete operating defaults for review; listing one here does not approve it.

## Execution and severity status

**Every case ID in this document, including each parameterized instance, has execution status: NOT EXECUTED.** “Expected” means a planned assertion, not an observed result. The decision model is also unimplemented; validating its JSON syntax is only an artifact check.

Recommended release severity for the engineering plan:

- **P0 — block release:** identity/booking confusion or duplicate creation (L04, L10–L11, I06, I12); unauthorized guest-list/recap/home/operator access (L06–L08, L15, A04/A07, P07/P15, H01–H07, C01); capacity/code/offer oversubscription (B04–B05, B09–B12, B15); entry bypass (A01–A06, I08–I09); duplicate/lost check-in or destructive deletion (P02, P05–P06, P12–P14); misleading/premature/duplicate or consent-violating messages (M02, M06, M08–M11). Any integrated path exposing these failures is also blocking.
- **P1 — required agreed behavior:** the remaining agreed surface continuity, RSVP management, notification discoverability, console controls, normal map/history and content flows must pass before claiming Events acceptance. An issue is not automatically acceptable just because it is not P0.
- **Design exploration / unapproved operating policy:** exact pin shape/glow/default window, cross-channel cadence/fallback, code-consumption moment, optional own-video, and other explicitly proposed defaults need a selected baseline before their corresponding assertions can be finalized. They are not treated as defects merely because a proposal was not selected. Once selected, their implementation inherits the appropriate functional severity.

These are internal review priorities, not a statement that a real issue has been reproduced or that the user approved every proposed procedure.

## Fixtures and evidence contract

Use a controlled clock and isolated test events, identities, codes, phones, media, and places. Do not send tests to real attendees or change live events. Reserve **Event A** for a public venue and **Event H** for a consented private home. Both have a single canonical place; the public place also has Event B so multi-event history can be checked. Preserve an older ordinary visit, its rating, audience, and explicit saved-place intent for the deletion/regression cases.

Create distinguishable identities: new guest; recognized confirmed guest; confirmed guest with expired/lost session; different-account guest; pending applicant; waitlisted guest; valid/expired offer holder; admitted guest without check-in; admitted guest with completed check-in; completed guest whose post was deleted; confirmed no-show; member blocked by another member; internal operator; and unauthorized non-operator. Missing-name, missing-username, optional-photo absence/failure, and unverified-current-phone are independent fixture switches.

Surface fixtures are **full app**, **App Clip**, and **browser fallback**, with actual platform invocation results recorded. Test installed/signed-out, installed/incomplete setup, fresh installation, and uninstall/reinstall separately. “Unknown identity” and “known identity with successful lookup and no booking” are different fixtures; a lookup timeout is neither of those successful outcomes.

Each implemented case must record its case ID, concrete fixture IDs, build/version, clock/time zone, platform/surface, action/result, server state assertions, notification outbox/delivery evidence where relevant, and pass/fail. Do not count a simulated wireframe click as an identity, upload, SMS, push, admission, or publication test. UI tests may use deterministic fakes; service integration and real platform handoff tests must be identified separately.

## Exit decision and coverage rationale

The specification has **121 named scenarios**: 17 link/state, 12 identity/setup, 16 codes/booking, 14 message-program, 11 admission, 17 post/media, 15 map/home, 7 console/regression, and 12 integrated paths. These are named acceptance specifications, not implemented or executed tests. Parameterized runs should report their actual instances separately.

The September 15 [engineering test plan](engineering-test-plan.md) and [case-to-test mapping](test-review/coverage-map.md) now map all 121 IDs plus 24 technical risk groups to planned files, assertions, layers and owners. [Mapping validation](test-review/mapping-verification.json) is an artifact check only; none of the future Events tests has been executed by this review. See the [QA journey guide](events-qa-test-plan.md) for tester-facing steps.

Coverage is organized around independent decisions and failure boundaries: actual surface, identity resolution, booking state, setup completeness, event/publication phase, admission, historical completion, notification capability/consent, capacity/code concurrency, map audience, and exact-location timing. The three-by-three event-detail comparison is deliberately paired with pending/waitlist/offer/loading cases; unknown identity is never collapsed into no RSVP. It is not credible to claim every possible combination of every axis has been tested. Engineering must add a targeted case whenever a new rule, provider behavior, or implementation risk creates a distinct outcome.

Before implementation is considered ready for release:

1. Map every active approved/derived requirement in the ledger to one or more implemented cases; explain anything legitimately covered by inspection rather than execution. New recordings supersede older conflicting requirements explicitly.
2. Resolve or explicitly exclude the listed proposed operating details from the release baseline; neither a proposed test nor a passing mock approves them. Keep historical product D7 (reconnection) and future privacy work deferred.
3. Run all applicable surface/state cases and integrated paths against the release candidate, with real public App Clip/full-app invocation validation and separate TestFlight evidence. Prior app release alone does not prove the released Clip exists.
4. Verify server-side state, permissions, idempotence, media references and message outcomes, not only visible screens. No unexplained failing case, unreviewed waiver, or missing high-risk authorization/concurrency boundary can be counted as passed.
5. Record the exact tested build, configuration, environments, evidence and remaining limitations. Passing this acceptance suite does not by itself prove zero defects; it establishes the agreed, traceable release boundary for Events.
