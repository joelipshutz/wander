## Distinct concepts

- **RSVP:** a free reservation/request for a particular event. Automatic confirmation is the default for available unprotected capacity; Astir can enable manual approval. Released spaces stay protected for Astir's selection while a waitlist exists. Pending requests/waitlist entries are not confirmed RSVPs. Confirmed RSVP unlocks the full guest list but does not prove attendance or unlock the recap.
- **Admission:** staff-recorded door attendance using the full-app event QR, or the approved confirmed-booking verification fallback when an installed-app guest cannot load their QR. This establishes eligibility for that event's recap, but does not create a place visit or complete event check-in.
- **Event check-in:** the attendee's explicit post-event submission. It creates one event-labeled personal post/place visit, marks the venue Been, and unlocks that event's recap for an eligible attendee. Optional fields may all be empty.
- **Personal public post:** the social representation of that same check-in, with event title/date, identity, note, and selected photos. Its default audience is everyone in Astir, subject to existing restrictions and private-venue protections. It is not a second submission or the shared event conversation.
- **Private feedback:** optional 1–5 stars plus an independently optional comment to Astir, excluded from public posts and venue ratings. A guest can skip either or both.
- **Protected recap:** the full shared event gallery and conversation. Access requires valid recorded admission and historical completion of check-in for this event. Personal-post deletion preserves that completion; it does not erase admission or grant access after attendance is invalidated.

“Derived invariant” means behavior needed to preserve an approved rule, not an additional product feature. Approvals through D35 are incorporated here, with D7 still deferred. The companion [product discovery draft](product-spec-draft.md) supplies routine proposed defaults, including reminder recovery, capacity administration, guest-list presentation, and editing. The review-detail column distinguishes those written but unapproved proposals from remaining design/engineering detail; it does not approve a proposal merely by referencing it.

## Explicit installed-app entry clarification — September 14

An invite link and an upcoming Events card both open the same event detail in the installed app. A confirmed event card opens its confirmed detail, while Show ticket opens QR directly. Resolve the current account’s booking status before offering an action; a link/card tap is not RSVP submission. Preserve the event through sign-in and collect only missing required data. The Already in Astir wireframes (local authoring source; authority retained in the requirements ledger) show these routes and status alternatives. This clarifies J01/J02 and existing identity/RSVP states; it does not change location, admission or recap permissions.
