# Events entry and App Clip performance review

**Status: source review only; no builds, benchmarks, runtime tests or service changes.** Inspected review checkout `f8d258e869503a28d70518a050dff36a344134c6` and the working Events engineering plan. D18A permits this review; it does not approve implementation or turn measurements into a pass. App code in this checkout is the previously identified `a0117cff` baseline; reconcile newer main before implementation.

The main recommendation is to keep the event detail/RSVP path independent of unrelated full-app work while preserving authoritative identity and booking checks. This implements D3A/D16A. It does not call for a store rewrite, different backend, relaxed admission, or a new authentication policy.

## Proposed critical path

These are implementation recommendations within the approved journeys, not measured behavior or finalized API signatures.

```text
Canonical event intent
  +--> permitted public event projection --> usable event detail
  +--> reuse/validate the legitimate session
          --> one coherent current guest/booking projection
          --> correct guest actions / missing essentials

Explicit RSVP
  legitimate identity + proof for the current phone
          --> authoritative RSVP operation (stable operation ID)
          --> returned booking state / truthful recovery
```

- Start the permitted public projection and legitimate session resolution concurrently where independent. Render event name, date, venue treatment and useful loading/recovery controls without waiting for a full hero image, guest gallery, social graph, full app history or media signing. Do not flash a no-RSVP state while identity is unknown.
- After validation, prefer a bounded guest-entry projection containing the needed booking/eligibility and entry-identity facts. Avoid client chains of profile → booking → per-person guest lookup → permissions → full guest list before the primary action can appear. Exact contract composition belongs to the shared contract owner; the guest list itself loads when opened and remains server-authorized.
- Required social sign-in, current-number SMS proof and authoritative eligibility/capacity checks are real serial dependencies. Reuse valid existing proof instead of re-verifying on every view, but do not infer it from a phone string. Fetch independent public content while the guest completes authentication; do not pre-create bookings or hold seats to mask latency.
- Let the successful RSVP command return its authoritative state so the screen does not immediately repeat the same lookup to discover what just committed. Message delivery can proceed from its durable intent; provider delivery must not hold confirmation UI open. Lost response uses the same operation identity/current-state recovery, never a fresh blind submit. A rejected token or rate limit must not cause a retry burst from several mounted views.
- Include only the shared styles/assets needed for event presentation in the Clip. Remote hero artwork should have an appropriate bounded rendition; eager recap/gallery/video or map/import SDK work is outside first-event detail. Keep the approved content available progressively; this is not a scope cut. Source byte counts, installed app size and Clip download size are different metrics and must not be substituted for one another.
- Guest web should expose usable permitted detail while authentication resolves, with route-specific code and bounded images; it should not download the staff console merely to render the guest page. There is no guest-web application here to profile yet. These are new-build requirements, not an observed JavaScript waterfall.

## Safe context and session reuse

[Wander/Services/Auth/AuthSessionProviding.swift:104](https://github.com/joelipshutz/wander/blob/f8d258e869503a28d70518a050dff36a344134c6/Wander/Services/Auth/AuthSessionProviding.swift#L104) intentionally persists only cached user ID/display name/handle. [Wander/Services/Auth/ClerkAuthService.swift:256](https://github.com/joelipshutz/wander/blob/f8d258e869503a28d70518a050dff36a344134c6/Wander/Services/Auth/ClerkAuthService.swift#L256) maps a failed session check plus cached identity to offline state, not verified remote access. [Wander/App/AppEntryView.swift:7](https://github.com/joelipshutz/wander/blob/f8d258e869503a28d70518a050dff36a344134c6/Wander/App/AppEntryView.swift#L7) has a 30-second foreground grace policy, used only for an already validated ready session at lines 197–207. None of these establishes RSVP ownership or phone proof across Clip, browser and app.

Persist minimal safe event intent separately from account-owned booking/draft/operation state. Coalesce concurrent lookups by the current account, event and request generation; reject obsolete responses after sign-out/account switching. Keep provider token caching and legitimate session reuse, without adding a second homemade identity cache. Do not extend the general foreground grace into a promise that capacity, an offer deadline, registration, cancellation or exact-home permission remains current.

A public event cache may contain only the permitted public projection, with a bounded freshness policy and invalidation for event edits/unavailability. Private booking/guest/location/media state stays account/event/permission scoped and revalidated when entitlement is uncertain. A cached event ID or confirmation must never authorize a guest action. Existing ordinary photo cache reads can precede networking ([Wander/App/WanderBackend.swift:651](https://github.com/joelipshutz/wander/blob/f8d258e869503a28d70518a050dff36a344134c6/Wander/App/WanderBackend.swift#L651)); copying that behavior unchanged into protected Events content is unsafe. D9 offline staff admission is its separately approved roster/queue mechanism, not a guest cache shortcut.

## Lean benchmark and feasibility plan

1. **Foundation proof before polishing.** Build the real minimal Clip with the chosen shared sources and actual provider dependencies. Record its archive/resource/dependency contributions and actual distribution-size reports, and validate them against current platform requirements during release preparation. Prove Apple and Google, verified phone, public invocation, failed invocation/browser fallback, install/icon launch and wrong-account recovery. No numeric platform limit or compatibility pass is asserted here.
2. **Instrument the first integrated slice.** Record invocation received, first usable permitted detail, session validated, guest state rendered, verification response received, RSVP submitted, authoritative result/recovery shown and QR ready. Trace duration, request count, response bytes, image decode/main-thread work and peak memory. Separate user typing/provider consent/SMS delivery time from app/server processing. The existing RPC signpost at [Wander/Services/Remote/WanderSupabaseClient.swift:344](https://github.com/joelipshutz/wander/blob/f8d258e869503a28d70518a050dff36a344134c6/Wander/Services/Remote/WanderSupabaseClient.swift#L344) and root timing at [Wander/App/WanderRootView.swift:3145](https://github.com/joelipshutz/wander/blob/f8d258e869503a28d70518a050dff36a344134c6/Wander/App/WanderRootView.swift#L3145) are useful seams, not existing Events measurements. Record no tokens, phone values, auth codes or protected payloads.
3. **Use a small explicit matrix.** Measure fresh Clip acquisition separately from cold-process launch and warm reopen; unknown/new and recognized/confirmed guests; full-app event link with small and large representative history; browser fallback; expired-token recovery and a lost RSVP response. Use a normal connection and a declared constrained network profile. Add one failed-network run to verify usable retry/context rather than reporting a successful latency. Repeat the same variants on the oldest supported representative phone and a current phone; real public/TestFlight invocation remain separate records.
4. **Baseline, then enforce the relevant regression.** Start with five repeated runs per primary variant, recording raw values, median and range; do not label a tiny sample as a dependable p95. Increase samples only for a noisy or failing branch. Compare the thin slice and completed journey under the same build/device/network conditions. New native performance tests can use the existing XCTest measurement pattern ([WanderUITests/MapFilterInteractionUITests.swift:273](https://github.com/joelipshutz/wander/blob/f8d258e869503a28d70518a050dff36a344134c6/WanderUITests/MapFilterInteractionUITests.swift#L273)); web traces should include navigation/paint/request timings. UI screenshot/mock speed is not a substitute.

Before measured latency targets are selected, use observable structural checks: unrelated maintenance is not awaited by Events entry; the Clip does not restore the full-app snapshot; duplicate consumers join one session/entry request; detail does not await full-list/gallery media; every result remains account-fenced; RSVP retry preserves one operation. These are proposed implementation checks, not invented benchmark passes. Capture an actual baseline before choosing numerical budgets or claiming an improvement.

## Decision status

**No new user choice is needed from this source review.** D3A/D16A already settle correct recovery and focused shared components; scheduling, bounded payloads, request coalescing, progressive loading and instrumentation are implementation work. Keep native-provider feasibility explicit. A genuine decision should return only if the measured Clip/provider/distribution proof cannot support the approved journey, or a demonstrated performance target requires a product-visible compromise. Do not preemptively replace the Clip with web, remove approved event content, waive identity checks or undertake an unrelated store rewrite.

Only this report was written. No Events performance result, native/provider feasibility result or release readiness is claimed.
