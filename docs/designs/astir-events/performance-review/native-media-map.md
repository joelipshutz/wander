# Native media, map and history performance review

September 15, 2026. **Source-only performance planning under D18A. No benchmark, runtime test, build, service request or production change was performed.** Baseline: `wander-events-flowchart-review` HEAD `f8d258e869503a28d70518a050dff36a344134c6`, with app code from `a0117cff6ed55a967f4212b45bb28d8c39ca1488`. The current Events plan already requires permission-aware caches, source removal, one canonical visit and the D16 focused/shared-native boundary. Proposed numbers below are starting measurement budgets, not approved limits, measured performance or release promises. The consolidated [measurement plan](measurement-plan.md) governs common fixture/reporting conventions; these media-specific stress probes supplement it.

## Recommendation

Use a small authorized first response, cursor pages, page-level enrichment, sized image variants and bounded media work. Extend the existing batching/cancellation idioms through Events-specific adapters; do not load the complete event gallery, every contributor’s visits or full videos before showing the recap. Keep the event completion/visit transaction independent of gallery hydration. This follows the selected architecture and requires no new user vote.

## Small, bounded loading proposal

1. **Event/recap entry:** one small current-viewer event state/projection first, with canonical place identity, current booking/admission/completion actions and permitted cover metadata. Load a first comments page and first gallery manifest independently; an image/transcode failure must not delay event identity or comments. Do not load protected metadata at all for a preview-only viewer.
2. **Gallery:** provisionally use 24–40 manifest items per page, a stable cursor with an ID tie-breaker, ID-based merge and one next-page request in flight. Keep thumbnails/posters for visible rows plus a small prefetch neighborhood. Do not eagerly loop through every cursor. Deleted-source tombstones and permission versions override an old page; retries cannot resurrect removed sources. Preserve a retryable page error rather than calling an outage the end of the gallery—the existing `PlaceProfileMapSurface.swift:1774` path sets `galleryHasMore = false` on a failed next page, which should not be copied as the Events policy.
3. **Media work:** begin with the existing four-image-download ceiling, at most one actively playing video and one upload at a time per account, then tune from device evidence. These are concurrency proposals, not restrictions on how many items a guest may select or keep. Use streaming/file-backed video, display-sized posters and finite decode jobs. Prioritize the selected/visible asset; release offscreen player resources and cancel obsolete prefetch.
4. **Upload:** persist a stable source/operation ID and file reference before transfer. Read/transform outside the main actor with bounded working memory; advance progress to “uploaded” only after server finalization. Retrying an already stored source finalizes metadata without sending the whole file again. Test kill/relaunch, access/source change during transfer and an item added while the queue drains. A background-completion promise, media duration/size cap or destructive recompression policy is not adopted by this recommendation.
5. **Map, place and feed:** return page/viewport summaries with event/place IDs, compact display data and authorized aggregate/engagement data. Load one selected event detail on expansion. A place initially gets its recent event-history page; further pages load on demand. Apply one Events completion result to existing history through the designated adapter, avoiding a second generic check-in and a full global rehydrate per upload or comment.
6. **Bound task ownership:** one active request per account/event/cursor or viewport request identity, duplicate coalescing for the same authorized media identity, cancellation on abandoned navigation, and explicit ownership of background user-selected upload work. Canceling a cell’s interest must not cancel an identical request still needed by another visible cell. A late result must pass current account/event/request/permission checks before caching or rendering.

## Privacy and history constraints are already decided

Permission/source-aware cache keys, current authorization for original/thumbnail/video-range bytes, immediate logical source invalidation, account-switch isolation and home-address expiry are requirements from the existing protected-data section, not performance options. A cache hit is not a permission check. The current [Wander/App/WanderBackend.swift:651](https://github.com/joelipshutz/wander/blob/f8d258e869503a28d70518a050dff36a344134c6/Wander/App/WanderBackend.swift#L651) memory/disk paths can return before network authentication, so they require an Events adapter rather than unconditional reuse. Retain [Wander/Services/Remote/WanderSupabaseClient.swift:230](https://github.com/joelipshutz/wander/blob/f8d258e869503a28d70518a050dff36a344134c6/Wander/Services/Remote/WanderSupabaseClient.swift#L230) expected-account checks around token retrieval and line 967 after downloads; also reject stale results at the Events cache/apply boundary. Existing decoded-image tasks may complete and cache before a canceled caller returns (`ListPlacePhotoResolver.swift:206–213`), which reinforces the need for current permission identity at cache insertion, not merely a cell cancellation flag.

Source removal should commit a tombstone/invalidated reference state promptly, then perform retryable physical derivative cleanup without loading the entire reference graph into a client. Every delivery observes current source/permission state. This keeps removal latency independent of deleting all stored bytes while preserving the approved behavior; a failed cleanup must not reauthorize a deleted source. No signed-URL TTL, CDN lifetime or offline cache allowance overrides the approved access rules. No claim to recall content already seen/copied is introduced.

Event history remains one canonical visit with no synthetic venue rating. Pagination, summary projections and cache invalidation cannot broaden old audiences, change independent notes/ratings/saves, drop historical completion after post deletion or invent another visit. The existing `WanderLocalStore.swift:8115` and `:8184` account/cancellation/local-mutation-revision guards are useful apply-boundary precedents.

## Product choices versus engineering requirements

No new user-facing architecture decision is needed to start bounded pages, batch enrichment, safe caches, cancelable work and file-backed media. If measurements show that acceptable gallery video cannot be delivered within the selected scope, return a concrete supported-format/duration/size or processing-delay tradeoff for review. Do not silently limit uploads, add Astir preapproval, change immediate visibility of successful uploads, enable/disable autoplay as a product decision, or remove the approved shared-gallery video capability. Personal-composer video remains separately proposed. Additional clustering/design changes, if needed for dense pins, should preserve the approved Featured/You/Friends semantics and be reviewed with actual density evidence.

Owners follow D8/D16: after-event/map owns gallery, history/cache adapters and associated console flows; shared-history integrator owns narrow existing-store/map seams; before-event/door supplies current admission/schedule results. No universal media framework, second backend or app-wide cache rewrite is proposed.
