## Surfaces and routes

- Canonical event link: `https://{event_link_domain}/events/{event_id}` is the current model's placeholder. Substitute the verified deployed domain and routing contract before testing; do not treat this as a live URL.
- App Clip event view and browser fallback: public preview, sign-in, RSVP, confirmed guest list and View/change RSVP.
- Full app Events tab: upcoming/past state, event detail, entry QR, explicit event check-in and recap.
- Full app map, place, profile and feed: event card, canonical place history and personal event post.
- Internal web console: Team admin access, event publishing/settings, approval/waitlist, invitation codes, scanner/roster, offline reconciliation and recap/moderation.

## Setup

Use a test event at a public venue, a consented private-home test event, and two events at the same place. Preserve an older ordinary visit with a different rating/note/audience. Use controlled accounts for new, pending, waitlisted, offered, confirmed, admitted, completed, deleted-post, no-show, blocked and revoked states, plus two Team admins and a nonadmin.

Run Apple and Google sign-in separately. Use real test phones/device accounts only for the identified device/provider checks. Do not send messages to real attendees or alter live events. Record exact builds, environment and evidence for every result; report a missing setup as blocked.

## Critical journeys

1. **No app:** invitation → Clip (or browser fallback) → Apple/Google → name/phone verification → RSVP → confirmation and reminders without installation. Guest list and management work when confirmed; the download offer is optional.
2. **Install later:** install from the event or app store, then try both link launch and app-icon launch. Recover the same reservation; collect only missing required name/username, allow skipping the photo, and show the QR under Events.
3. **Already installed:** open the invitation and separately discover the event in Events. Preserve the correct account/event state. An expired or different session offers original-account recovery without creating another reservation.
4. **Capacity/code/offer:** exercise pending, waitlist and selected offer states. Offers hold their promised spot. Accept once, retry after a lost response and test expiry. Pending/waitlist consumes no code use; confirmation consumes one; successful cancellation returns it once. Disabling a code blocks new submissions while already-submitted guests retain code eligibility.
5. **Change and late arrival:** move an upcoming event to a new future date. Keep confirmed guests confirmed, notify them and allow cancellation. At a 7–10 pm event, a 7:15 guest can still complete normal RSVP/entry unless the console set an earlier close. Self-cancellation still closes at event start.
6. **Door online/offline:** scan the confirmed installed-app guest; retry/duplicate and approved lookup fallback. Prepare a roster online, then lose connectivity. Local admissions say awaiting sync, survive a reload and reconcile visibly. Cancellations/admin changes after download must produce the correct conflict; a missing roster cannot invent confirmation.
7. **After the event:** publish recap, receive the notice, complete the explicit event check-in with every optional field empty. Get one event-labeled place visit and no venue rating, then open protected recap. A no-show cannot unlock it by self-report.
8. **Media/history:** add permitted photos/videos, use a gallery photo in the personal post, remove its source and check every reference. Delete the personal post while preserving valid historical completion and independent old place history.
9. **Private home/map:** test before reveal, during access and after expiry across app/Clip/browser/map/place and share/calendar previews. Approximate views must not contain hidden exact data. Check Featured/You/Friends rules without inventing second-degree expansion.
10. **Whole loop and recovery:** run E01–E12 from the acceptance criteria through real account, server, admission, check-in and persistence boundaries. A collection of separately passing mock screens is not an integrated pass.

## Interactions and failure checks

- Double tap, back, dismiss, close/relaunch, slow request, no connection, server failure and a lost successful response.
- Wrong/expired verification code, changed number, interrupted provider sign-in, account switch during a request and a successful lookup returning no RSVP versus a failed lookup.
- Offer expiry and registration close immediately before/at/after the boundary; two guests competing for the last seat/code use; an offer awaiting a lock until after its deadline.
- SMS/push denied, unavailable or opted out: show current state by link/Events; no false delivery, consent override or canceled reservation merely from missing notifications.
- Empty event list, no nearby events, long titles, keyboard, small screen, large text, screen reader, dark mode and reduced motion.
- Unauthorized direct requests, stale caches and already-open pages after sign-out, account switch, revoked admission/admin access, source removal or home-address expiry.
- Upload failure preserves an honest retry state; failure never shows content as saved or quietly drops selected media.
